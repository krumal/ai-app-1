# Урок 4. Делаем репозиторий AI-Native

Формат: рыба сценария для будущих слайдов.  
Главная рамка: **harness engineering** — мы не просто просим агента писать код, а проектируем среду, в которой он может работать предсказуемо.

Основа сценария:

- OpenAI, Harness Engineering: https://openai.com/index/harness-engineering/
- Ian Bull, Software Architecture in the Age of AI: https://ianbull.com/posts/software-architecture/

## 1. Тема урока

**Тезис:** AI-Native repository — это репозиторий, который помогает агенту понять проект, соблюдать правила, менять код и проверять результат.

- AI-Native repo;
- harness engineering;
- instructions;
- docs / memory bank;
- quality gates;
- feedback loop.

- В прошлых темах мы говорили про skills, MCP, безопасность, debug и bugfix.
- Теперь говорим про сам репозиторий.
- Главная идея: агенту нужен не только prompt, а рабочая среда вокруг проекта.

## 2. Почему обычного repo недостаточно

**Тезис:** в обычном проекте слишком много знаний живёт не в коде, а в головах команды.

- как запустить проект;
- какие команды безопасны;
- где менять фичу;
- какие есть архитектурные границы;
- какие правила у команды;
- какие продуктовые нюансы важны.

- Проблема всех репозиториев в том, что бОльшая часть инфы о проекте не хранится в этом репозитории, а хранится в лучшем случае в jira / confluence, а в худшем - в головах синьоров или переписках в slack / telegram.
- Когда разработчик пытается поставить задачу AI агенту, то он часто представляет, что общается с коллегой, который как и он сам находится на таком же уровне понимания проекта. Многая инфа о проекте хранится на подсознательном уровне у разработчика в голове и при постановке задачи бывает сложно определить, какую инфу о проекте агент знает, а какую нет.
- Выход - делать репозиторий AI native – это значит дать в инструкциях к репозиторию всю необходимую информацию или ссылки и инструменты к другим хранилищам этой информации, куда агент смог бы добраться чтобы получить больше контекста о решаемой задаче

## 3. Harness Engineering

**Тезис:** разработчик всё меньше пишет каждую строку руками и всё больше проектирует среду, в которой агент может работать.

- humans steer;
- agents execute;
- repo gives context;
- tools give actions;
- checks give feedback.

- В феврале OpenAI выпустили хорошую статью которая систематизирует подходы которых я придерживался несколько месяцев до этой статьи
- Называется Harness Engineering
- Суть заключается в том, что человек задаёт направление, правила, ограничения и критерии качества для агента
- А агент выполняет работу внутри этой среды: читает контекст, пишет код, запускает проверки, исправляет ошибки.

## 4. Репозиторий как harness

**Тезис:** AI-Native repo — Это способ организовать проект так, чтобы в нём смог ориентироваться как агент, так и новый разработчик

```text
AI-Native Repo
├─ AGENTS.md
├─ .memory-bank/
├─ ...
└─ .tasks/
```

- Этим репо сможет пользоваться и новичок (человек) и агент
- Дальше разберём каждый слой этого harness.

## 5. Проект должен быть читаемым для агента

**Тезис:** для агента существует только то, что он может прочитать или получить через tools.

- markdown файлы
- доступ по api к 3rd party services
- mcp
- skills

- Если знание лежит только в голове разработчика или в старом Slack-треде, агент его не знает.
- Это основа AI-Native repo: сделать проект читаемым.

## 6. AGENTS.md как входная точка

**Тезис:** `AGENTS.md` — это короткая входная инструкция и карта проекта для агента.

- где искать документацию;
- какие команды использовать;
- package manager;
- правила проверки;
- запреты на опасные действия;
- куда идти за деталями.

- `AGENTS.md` не должен быть энциклопедией.
- Его задача — дать агенту стартовые правила и направить в нужные документы.
- Если правило часто повторяется в задачах, его стоит перенести сюда.
- `AGENTS.md` — это инструкция для Codex внутри проекта: правила, команды, стиль кода, структура репозитория, тесты, запреты и рабочие договорённости.
- Это аналог `README.md`, но не для людей, а для coding agent.
- Codex читает `AGENTS.md` перед началом работы, чтобы понимать контекст проекта без повторного объяснения в каждом prompt.

## 7. Как подключается AGENTS.md

**Тезис:** инструкции собираются слоями: от глобальных к локальным.

- `~/.codex/AGENTS.md`;
- `repo/AGENTS.md`;
- `repo/apps/web/AGENTS.md`;
- приоритет инструкций;
- перезапуск после изменений.

- Инструкции загружаются при старте run/session
- Codex не следит за изменениями `AGENTS.md` в реальном времени. Если файл изменился, лучше начать новую сессию или перезапустить Codex.
- Есть глобальный уровень: `~/.codex/AGENTS.md`. Он применяется ко всем проектам пользователя.
- Есть проектный уровень: `AGENTS.md` в корне репозитория и во вложенных директориях.
- Инструкции склеиваются в один общий блок: сначала глобальные, потом проектные от корня к текущей директории.
- Прямые инструкции пользователя в чате важнее, чем `AGENTS.md`.
- System/developer инструкции среды важнее, чем `AGENTS.md`.
- Агент обычно не видит `AGENTS.md` как список файлов с путями. Он получает уже склеенный текст инструкций.

пример как это видит агент:
"""

# AGENTS.md instructions for /path/to/cwd

<INSTRUCTIONS>
...текст global AGENTS...
 
--- project-doc ---

...текст root AGENTS...

...текст nested AGENTS...
</INSTRUCTIONS>
"""

- Если важно, чтобы агент понимал источник правила, подпишите это внутри файла: например, `# Root AGENTS.md` или `# services/payments/AGENTS.md`.
- Хороший `AGENTS.md` отвечает на вопросы: как установить зависимости, как запустить проект, как прогнать тесты, где лежит важный код, чего нельзя делать.
- Плохой `AGENTS.md` содержит длинную философию, устаревшие команды, противоречивые правила и слишком много текста.
- Самая полезная форма правил: конкретные команды и ограничения, например `Use pnpm`, `Run npm test before final response`, `Do not edit migrations`.

## 8. Progressive Disclosure

**Тезис:**
- Т. к. AGENTS.md в codex загружается сразу при старте сессии и часть инструкций которые в nested папках могут быть не актуальны для текущей задачи.
- Поэтому стоит использовать подход с Progressive Disclousure.
- агенту не нужно читать всё сразу. Контекст должен раскрываться слоями.
- для этого можно например создавать индексные файлы (index.md) которые будут являтся table of contents текущей директории (и возможно вложенных директорий тоже)

- `index.md`;
- overview;
- architecture map;
- module docs;
- deep dives;
- external sources.

- Сначала агент читает короткий overview.
- Потом по ссылкам уходит в нужный раздел.
- Это экономит контекст, когнитивные способности агента и помогает ему не теряться в лишних деталях.

## 9. Инструкции рядом с кодом

**Тезис:** часть инструкций может жить рядом с конкретной областью проекта.

- root `AGENTS.md`;
- инструкции в папках;
- README модулей;
- локальные правила для frontend/backend/infra;
- примеры изменений.

- У разных частей проекта могут быть разные правила.
- Корневой файл задаёт общую карту, а локальные инструкции уточняют детали.
- Это снижает шанс, что агент применит общее правило там, где есть локальное исключение.

## 10. Memory Bank

**Тезис:** memory bank — это база знаний проекта для агента.

- project overview;
- architecture;
- infrastructure;
- tech stack;
- product features;
- conventions;
- operations.
- Главная цель — вынести неявное знание в текст.
- Агент должен понимать не только код, но и почему проект устроен именно так.
- Документацию лучше делить семантически: по смыслу, а не как случайный dump.
- Лучший лайфхак - проектировать memory bank как для человека. Т. е. чтобы человек без использования AI мог бы пройтись по дереву документации и найти ответ на свой вопрос
- обязательно применять подход с progressive disclousre

## 11. Что добавлять в memory bank

**Тезис:** добавляем то, что помогает агенту принимать правильные решения.

- как устроен продукт;
- основные user flows;
- архитектурные границы;
- интеграции;
- инфраструктура;
- команды и проверки;
- важные trade-offs (ADR).
- код сам по себе является хорошей документацией к проекту, но часто его недостаточно, и поэтому memory bank должен помогать агенту разобраться с проектом, а не заменять или дублировать информацию из кода
- простое правило - если на поиск информации по коду вы тратите несколько минут и прыгаете по функциям и классам, то возможно эту информацию стоит вынести в memory bank
- Если знание влияет на изменение кода, его стоит описать.
- Если человек объясняет это новичку, агенту это тоже нужно.
- Хороший критерий: поможет ли это агенту не сломать проект?

## 12. Что не добавлять в memory bank

**Тезис:** memory bank не должен быть мусорной корзиной для всего подряд.

- устаревшие решения;
- дубли кода;

- Главный риск memory bank — устаревание.
- Лучше меньше, но актуальнее.
- Всё, что быстро протухает, должно жить в task-контексте или обновляться автоматически.

## 14. Onboarding skill

**Тезис:** Перед тем как начать сессию, агент обязательно должен узнать о том, как именно у нас выглядит структура проекта, где у нас находится карта проекта. И можно это сделать либо положив нашу карту проекта в AGENTS.md, либо если она становится довольно-таки большой, то мы ее кладем в memory bank.

При старте сессии необходимо заставить агента ознакомиться с этой картой репозитория. И это называется onboarding. То есть это когда мы просим агента пойти в memory bank, почитать его основной файл index.md, посмотреть последний гит-коммит в гетке и вернуться.  onboarding заставляет агента сначала изучить проект, а не сразу менять код.

- прочитать `AGENTS.md`;
- просмотреть docs / memory bank;
- изучить структуру repo;
- посмотреть последние commits;
- отчитаться о готовности.

- Onboarding skill нужен, чтобы агент вошёл в контекст проекта перед задачей.
- Он должен изучить проект “по верхам”, найти основные документы и понять текущую историю изменений.
- В конце агент должен сказать, что он понял, и где может быть риск непонимания.

Пример такого скилла:
"""
---
name: onboarding
description: "Run this skill to get familiar with the project"
---

Get familiar with this project by performing the following steps:

1. Read `.memory-bank/index.md` to understand the overall project idea, structure, architecture, code patterns and other important things to maintain this project.
2. Review recent code changes to understand the current development state.

After that, say "Onboarding complete" and briefly describe the project overview and current status.
"""

## 18. Архитектура как инструкция для AI

**Тезис:** дальше переходим от документации к самой структуре кода: для агента архитектура проекта становится одной из главных инструкций.

- до этого мы говорили о том, как дать агенту контекст через инструкции и документацию;
- но агент читает не только markdown-файлы, он читает сам код и структуру проекта;
- структура кода — это самый важный prompt, который проект даёт AI;
- И в кодинге с агентами очень хорошо помогают подходы Clean Code, Clean Architecture, DDD и modular architecture;
- код с понятными границами, низкой связностью и предсказуемым направлением зависимостей становится более полезным чем раньше

- Главная мысль: AI каждый раз заходит в проект как новый разработчик без накопленной памяти.
- Он не знает историю решений и не чувствует скрытые связи между модулями.
- Поэтому архитектура должна помогать ему понять систему снаружи внутрь, а не заставлять трассировать неочевидные side effects по всему проекту.

## 19. Код для AI должен быть понятным

**Тезис:** при разработке с AI нам особенно нужен код, который легко читать, локально менять и проверять.

- явные границы модулей;
- честные интерфейсы;
- низкая связность;
- высокая связность внутри модуля;
- предсказуемое направление зависимостей;
- локальность изменений.

- Это очень похоже на то, о чём давно говорят Clean Code и Clean Architecture.
- Но при работе с AI эти принципы становятся не просто вопросом красоты кода, а вопросом управляемости агента.
- Чем понятнее границы и зависимости, тем проще агенту понять, где нужно менять код и какие последствия будут у изменения.
- Если модуль можно понять через публичный интерфейс и контракт, агенту не нужно читать половину проекта, чтобы сделать маленькую правку.

## 20. Side effects должны быть явными

**Тезис:** код для AI должен минимизировать скрытые каскады и делать побочные эффекты видимыми.

- input и output понятны;
- внешние вызовы явно отделены;
- изменения состояния видны в коде;
- нет скрытых цепочек действий;
- меньше blast radius;
- проще локально проверить результат.

- Для человека скрытый side effect тоже проблема, но опытный разработчик может помнить контекст проекта.
- Агент такого контекста не чувствует. Он видит локальный участок кода и пытается вывести поведение из структуры.
- Если функция незаметно запускает цепочку действий в других частях системы, агенту нужно восстановить всю цепочку последствий.
- Чем меньше скрытых каскадов, тем безопаснее агенту менять код и тем проще построить feedback loop через тесты, логи и локальную проверку.

## 21. Progressive Disclosure of Complexity

**Тезис:** архитектура должна раскрываться по уровням детализации.

- top-level services;
- public interfaces;
- types / contracts;
- implementation;
- tests.

- На верхнем уровне агент должен видеть понятные сервисы и границы.
- Если нужно больше деталей, он идёт к контрактам и типам.
- В реализацию он проваливается только тогда, когда реально нужно менять код.

## 22. C4 model

**Тезис:** C4 model помогает дать агенту карту системы от общего к частному.

- Context;
- Containers;
- Components;
- Code;
- links to docs.

- C4 хорошо ложится на Progressive Disclosure.
- Сначала агент смотрит context, потом containers, потом components.
- Это особенно полезно для больших проектов и интеграций.

## 23. Продуктовые фичи

**Тезис:** агенту нужно понимать продукт, а не только техническую структуру.

- user roles;
- user stories;
- core flows;
- business rules;
- feature ownership;
- edge cases;
- examples.

- Как только мы даем агенту более богатый контекст о нашем проекте – дополняем это инфой о продукте, то становится проще работать с проектом и реализовывать разные идеи
- Многие ошибки агента происходят из-за непонимания продукта.
- Если есть описание фич, ролей и бизнес-правил, агенту проще менять код осмысленно.
- Продуктовая документация должна быть такой же доступной, как техническая.

## 24. Внешние источники знаний

**Тезис:** не всё должно лежать в репозитории, но агенту нужно знать, где искать.

- Confluence;
- Jira;
- GitHub issues;
- Slack decisions;
- design docs;
- API docs.

- Если часть знаний живёт во внешних системах, нужно дать агенту доступ или инструкции.
- MCP/connectors могут помочь подключить Jira, Confluence, Drive, GitHub.
- Важно явно указать, какие источники считаются authoritative.

## 25. Документация должна обновляться

**Тезис:** устаревшая документация хуже отсутствующей.

- Описать проект один раз несложно.
- Главная сложность — поддерживать знания актуальными.
- Если документация врёт, агент будет уверенно делать неправильные выводы.
- как это делать? проще всего обновлять документацию вместе с реализацией новых задач
- второй способ - создать automations которые будут раз в несколько дней проверять последние коммиты и смотреть что из документации стоит обновить

## 28. Итоговая схема

**Тезис:** AI-Native repo — это harness вокруг агента.

**На слайде:**

```text
AGENTS.md            -> вход и правила
docs / memory bank   -> знания проекта
.tasks               -> task context
onboarding skill     -> старт сессии
quality gates        -> проверки
dev tools            -> feedback loop
architecture         -> понятные границы
freshness loop       -> актуальность знаний
```

**Что сказать:**

- Репозиторий должен помогать агенту понять задачу, найти знания, изменить код и проверить результат.
- Это не заменяет разработчика.
- Это снижает количество ручного объяснения и повышает предсказуемость работы агента.

## 29. С чего начать процесс подготовки репо в AI Native репо?

1. Описать тех стек и инфру
2. Попросить агента изучить репозиторий top down и создать c4 l1-l3 level архитектуру для основных модулей проекта
3. Описать основные user stories:
>Как голодный пользователь,Я хочу отфильтровать рестораны по времени доставки «до 30 минут»,Чтобы успеть поесть во время моего короткого перерыва.
4. Проверить, какая ещё документация о проекте уже существует и подумать, как можно было бы дать агенту доступ к ней
5. если есть уже skills с code guidelines, code review, etc, то залинковать их в этом memory bank
6. Составить .memory-bank/index.md и другие index.md с table of contents для навигации по репозиторию и memory bank
