# User Stories

## US-01. Подключить локальный проект

Как пользователь, я хочу выбрать локальный репозиторий через системный picker, чтобы LocalTasks начал читать задачи из его `.tasks` директории.

### Путь пользователя

1. Пользователь открывает LocalTasks.
2. Если активный проект еще не выбран, пользователь видит empty state `No project selected`.
3. Пользователь нажимает кнопку `+` в правой части верхней панели.
4. Приложение открывает системный диалог выбора директории.
5. Пользователь выбирает локальный репозиторий.
6. Backend добавляет проект в `~/.config/localtasks/config.json` и делает его активным.
7. UI сбрасывает поиск, фильтр списков и открытые карточки.
8. Приложение загружает board для выбранного проекта.
9. Если в репозитории есть `.tasks`, пользователь видит kanban-доску.
10. Если `.tasks` нет, пользователь видит empty state с путем, где нужно создать директорию.

### Результат

Проект появляется в project dropdown, становится активным и готов к просмотру задач.

## US-02. Смотреть kanban-доску задач

Как пользователь, я хочу видеть списки и карточки, построенные из `.tasks`, чтобы ориентироваться в текущей работе по проекту.

### Путь пользователя

1. Пользователь открывает приложение с уже выбранным активным проектом или выбирает проект из dropdown.
2. Приложение запрашивает конфиг и board активного проекта.
3. Пока backend сканирует файловую систему, пользователь видит состояние `Loading board...`.
4. Backend читает `<repo>/.tasks`, собирает списки, карточки, дерево файлов, timestamps и labels.
5. UI показывает верхнюю панель со статистикой `L / C`, поиском, фильтрами списков, кнопкой reload и labels.
6. Пользователь видит board columns:
   - root `task-*` директории попадают в список `Tasks`;
   - остальные root-директории становятся отдельными списками;
   - одиночные root-файлы попадают в `Misc`.
7. В каждой колонке пользователь видит количество карточек.
8. На карточках пользователь видит название, путь, labels, дату обновления и количество markdown-файлов.
9. Пользователь может отфильтровать доску по конкретному списку через filter pills.
10. Пользователь может найти нужную карточку через поиск по названию, пути, labels и файлам.
11. Если поиск ничего не нашел, пользователь видит empty state `No matches`.
12. Если в `.tasks` нет карточек, пользователь видит empty state `Empty board`.

### Результат

Пользователь получает актуальную навигационную картину задач проекта, собранную из файловой структуры `.tasks`.

## US-03. Открыть карточку задачи

Как пользователь, я хочу открыть карточку, чтобы увидеть ее путь, даты, labels, статистику и связанные файлы.

### Путь пользователя

1. Пользователь находится на kanban-доске активного проекта.
2. Пользователь находит нужную карточку визуально, через фильтр списка или через поиск.
3. Пользователь нажимает на карточку.
4. Приложение открывает card modal.
5. Если у карточки есть primary markdown-файл, приложение автоматически загружает его содержимое.
6. В header модалки пользователь видит список, название карточки, относительный путь и назначенные labels.
7. Пользователь видит статистику карточки: дату создания, дату обновления, количество файлов, папок и markdown-файлов.
8. В левой части модалки пользователь видит дерево файлов карточки.
9. В правой части модалки пользователь видит preview открытого файла или предложение открыть primary doc.
10. Пользователь может назначить или снять labels через label menu внутри модалки.
11. Пользователь закрывает модалку через крестик, клик по фону или Escape.

### Результат

Пользователь переходит от краткого представления карточки на доске к полному контексту задачи и ее файлов.

## US-04. Открыть и прочитать файл карточки

Как пользователь, я хочу выбрать файл из дерева карточки и прочитать его содержимое, чтобы изучить задачу, заметки или артефакты.

### Путь пользователя

1. Пользователь открывает карточку задачи.
2. Приложение показывает дерево файлов карточки.
3. Если у карточки есть primary markdown-файл, он открывается автоматически.
4. Если primary-файла нет, пользователь выбирает нужный файл вручную из дерева.
5. При клике по файлу UI показывает состояние загрузки preview.
6. Backend читает файл внутри task root и возвращает содержимое, формат, путь и даты создания/обновления.
7. Если файл markdown, UI показывает отрендеренный preview через `ReactMarkdown` и `remark-gfm`.
8. Если файл не markdown, UI показывает содержимое как plain text.
9. Пользователь видит путь открытого файла, формат и file metadata.
10. Пользователь может переключаться между файлами в дереве, оставаясь внутри карточки.
11. Если файл не удалось открыть, пользователь видит error state в preview pane.

### Результат

Пользователь читает реальные файлы из `.tasks` без перехода в редактор кода или файловый менеджер.

## US-05. Редактировать файл карточки

Как пользователь, я хочу изменить содержимое открытого файла и сохранить его обратно в `.tasks`, чтобы обновлять задачу прямо из LocalTasks.

### Путь пользователя

1. Пользователь открывает карточку задачи.
2. Пользователь открывает нужный файл из дерева файлов.
3. В preview pane пользователь нажимает `Редактировать`.
4. UI переключает файл в режим редактирования и заполняет editor текущим содержимым файла.
5. Пользователь изменяет текст файла.
6. Для markdown-файлов пользователь может использовать toolbar:
   - bold;
   - italic;
   - heading;
   - bullet list;
   - inline code;
   - code block;
   - link;
   - quote.
7. Для markdown-файлов пользователь может переключиться на `Live Preview`, чтобы проверить результат до сохранения.
8. Пользователь нажимает `Save`.
9. UI показывает состояние сохранения.
10. Backend записывает новое содержимое в файл внутри `.tasks`.
11. Для markdown-файлов backend сохраняет существующий frontmatter и обновляет только тело файла.
12. Backend перечитывает файл, пересобирает board и возвращает свежие данные.
13. UI выходит из режима редактирования, показывает обновленный preview и обновляет состояние доски.
14. Если сохранение не удалось, пользователь остается в редакторе и видит error state.
15. Пользователь может нажать `Cancel`, чтобы выйти из режима редактирования без сохранения.

### Результат

Пользователь обновляет содержимое task-файла из интерфейса, а доска остается синхронизированной с файловой системой.

## US-06. Получать realtime-обновления открытого файла

Как пользователь, я хочу видеть внешние изменения открытого файла без ручного reload, чтобы LocalTasks оставался синхронизированным с редактором кода или другим процессом.

### Путь пользователя

1. Пользователь открывает карточку задачи.
2. Пользователь открывает файл из дерева или приложение автоматически открывает primary markdown-файл.
3. Frontend держит один WebSocket connection для активной card modal и подписывается только на текущий `projectId`, `cardRelativePath`, `fileRelativePath`.
4. Если файл изменился на диске, backend через `chokidar` debounce-ит событие, перечитывает файл, пересобирает board и отправляет `file:updated`.
5. В reading mode UI автоматически заменяет preview содержимым с диска и обновляет board metadata.
6. Если пользователь переключился на другой файл, frontend отписывается от предыдущего файла, подписывается на новый и игнорирует stale-события для старого пути.
7. Если пользователь закрыл card modal, frontend убирает активную подписку.
8. Если файл изменился на диске во время edit mode, UI не перезаписывает несохраненный editor text.
9. В edit mode пользователь видит предупреждение `File changed on disk` и кнопку `Reload from disk`.
10. При нажатии `Reload from disk` editor получает последнюю версию с диска, а предупреждение исчезает.
11. Если открытый файл удален или стал нечитаемым, UI показывает file-level error pane с относительным путем файла и применяет свежий board, если backend смог его вернуть.

### Результат

Пользователь видит актуальный preview открытого файла, не теряет несохраненные правки в editor mode и получает понятное состояние для удаленного или нечитаемого файла.

## US-07. Сгенерировать AI digest

Как пользователь, я хочу сгенерировать markdown digest по задачам за выбранный период, чтобы быстро понять, над чем шла работа, какой есть прогресс, проблемы и следующие шаги.

### Путь пользователя

1. Пользователь находится на kanban-доске активного проекта.
2. Пользователь нажимает кнопку `AI digest` в правой части верхней панели.
3. Приложение открывает modal `AI digest`.
4. Modal по умолчанию выбирает текущую неделю в локальной timezone.
5. Пользователь может выбрать период:
   - `Current week`;
   - `Previous week`;
   - `Custom range`.
6. Frontend вызывает `/api/projects/:id/digest/preview`.
7. Backend выбирает карточки, у которых `card.updatedAt` попадает в inclusive date range.
8. Modal показывает список задач, которые войдут в digest: название, список, дату обновления, labels, количество файлов и пути файлов.
9. Карточки, входящие в preview digest, подсвечиваются на доске, пока modal открыт.
10. Для `task-*` карточек backend включает только `plan.md` и `implementation_progress.md`; `draft.md` не передается в LLM.
11. Для остальных карточек backend включает все поддерживаемые markdown/text-файлы карточки.
12. Пользователь нажимает `Generate digest`.
13. Modal показывает состояние генерации.
14. Когда ответ готов, UI рендерит markdown digest.
15. Пользователь может скопировать digest через кнопку `Copy`.
16. Если задач за период нет, пользователь видит empty state `No tasks updated in this period`.
17. Если API key отсутствует или provider вернул ошибку, modal остается открытой и показывает error state.

### Результат

Пользователь получает AI-generated markdown digest за выбранный период без сохранения результата обратно в `.tasks`.

## US-08. Сгенерировать Scrum Poker оценку для задачи

Как пользователь, я хочу получить AI-помощь в оценке сложности задачи прямо из карточки, чтобы быстрее понимать размер работы и принимать решения по планированию.

### Путь пользователя

1. Пользователь открывает карточку из списка `Tasks`.
2. Карточка отмечена как eligible для оценки, если это root `task-*` директория со `draft.md` и `plan.md`.
3. Для eligible карточки пользователь нажимает `Generate estimate`.
4. UI показывает состояние загрузки.
5. Backend запускает 5 параллельных participant-запросов к LLM (backend engineer, frontend engineer, QA engineer, tech lead, product-minded implementation reviewer), валидирует ответы и считает median/average.
6. Backend сохраняет результат в `<task>/estimate.json`.
7. API возвращает `TaskEstimate` и свежий board.
8. UI обновляет открытый card modal и показывает бейдж вида `N pts` без перезагрузки страницы.
9. Пользователь открывает decision log через popover с итогом, средним значением и списком голосов.
10. Пользователь может нажать `Regenerate estimate`, чтобы пересчитать оценку с тем же процессом.
11. При количестве валидных голосов меньше 3 пользователь видит ошибку и предыдущая сохраненная оценка остается неизменной.

### Результат

Пользователь получает быстрый и компактный ориентир по сложности задачи, который хранится рядом с задачей, обновляется только внутри `.tasks/task-*/estimate.json` и отражается в UI без перезагрузки.
